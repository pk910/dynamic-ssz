# Contributing to Dynamic SSZ (dynssz)

First off, thank you for considering contributing to dynssz! Contributions of all kinds are welcome: bug fixes, new features, documentation improvements, or additional test coverage. If you're looking for a place to start, take a look at the open issues.

## Getting Started

You need Go 1.22 or later. Clone the repository and run the unit tests to verify your setup:

```bash
git clone https://github.com/pk910/dynamic-ssz.git
cd dynamic-ssz
make test
```

## Development Workflow

The Makefile provides the main entry points (run `make help` for the full list):

| Command | Description |
| ------- | ----------- |
| `make build` | Build the `dynssz-gen` CLI into `bin/` |
| `make test` | Run unit tests with the race detector |
| `make spec` | Run the Ethereum consensus spec tests (downloads test vectors on first run) |
| `make fuzz` | Run a 30s differential fuzzing smoke test (reflection vs. generated code) |
| `make bench` | Run library benchmarks |
| `make lint` | Run `go vet` and check formatting |
| `make fmt` | Format the code |

### Linting

CI runs [golangci-lint](https://golangci-lint.run/) with the strict configuration in [.golangci.yml](.golangci.yml). To check your changes locally before pushing:

```bash
golangci-lint run
```

### Backward Compatibility Tests

The library guarantees that code generated by older releases keeps working with newer library versions (see the versioning policy in [SECURITY.md](SECURITY.md)). CI verifies this against archived generator output from every previous v1.x release. To run these tests locally:

```bash
make unpack-compat-tests
go test ./codegen/compat-tests/...
```

If you change the code generator or the runtime interfaces it targets, make sure these tests still pass — they are the compatibility contract with existing users.

## Ground Rules & Expectations

- Follow the existing coding style: descriptive names, godoc comments on exported symbols, and error handling consistent with the surrounding code.
- New functionality needs tests. If you touch the code generator, cover both the reflection and codegen paths — the differential fuzzer and spec tests compare them against each other.
- Do not introduce breaking changes to the public API; the library follows semantic versioning and v1.x must remain backward compatible.
- Update the documentation ([README.md](README.md) and the relevant pages in [docs/](docs/)) when you change or extend the public API, struct tags, or CLI flags.
- Before submitting a pull request, make sure `make test` and `golangci-lint run` pass locally.
- Participate in code reviews and respond to feedback in a timely manner.

## How to Contribute

1. Fork the repository and clone your fork.
2. Create a new branch for your changes.
3. Make your changes and commit them with clear, descriptive commit messages.
4. Push your branch and open a pull request against the main dynssz repository.
5. Wait for CI results and feedback from the maintainers.

## Reporting Issues

If you find a bug or have a feature request, please use the GitHub issue tracker. Before creating a new issue, do a quick search to see if the problem has already been reported — if it has, add a comment to the existing issue instead of opening a new one.

For security vulnerabilities, please follow the responsible disclosure process in [SECURITY.md](SECURITY.md) instead of opening a public issue.
